## 收到 DSH 交付后的 Review

1. **范围**：核对只做 iOS 项目骨架、Home、创建项目、编辑器/设置占位、基础导航与项目模型。不得提前加入导入、拼贴、AI、导出或最终品牌视觉。
2. **架构**：检查 SwiftUI 视图、导航状态、ProjectStore 与可序列化模型的职责。查找空协议、空服务、过度目录化、大型依赖及无批准的公开接口变化。
3. **Bug 与数据**：实测创建、重命名、打开、返回与近期列表；若近期列表只在内存中，界面不得暗示永久保存。核查编码/解码、异常状态和是否存在编译警告。
4. **性能与视觉**：核查主线程无不必要耗时工作，基本交互响应及时；界面中性、清楚、iOS 原生，触控尺寸、VoiceOver 与安全区域可用。
5. **证据**：看实际测试日志、构建结果、启动步骤与运行截图。Windows 上无法构建 iOS 应用；未运行的测试不得记为通过。

## 待 Architect 决定，不影响 DSH 当前执行

- 原始 Prompt 要求 Stage 01 验收文件在创建时写 `WAITING_FOR_USER`。Review 时应区分“DSH 已交付”与“ChatGPT Review 已通过、可交给用户验收”；后者完成前，文件状态不得被当成阶段已通过。若 DSH 按原文填写，这属于 Prompt 状态定义问题，不作为 DSH 擅自越权的证据。
- 原始路线图把静态导出排在动态系统之后。Stage 01 只记录路线图草案，后续 Stage 在本阶段获用户批准后再调整；静态渲染与导出应先于动态系统验证。
- 原始 Prompt 要求多份治理文档与目录。Review 重点看内容真实、简洁，不能因为目录存在就误判架构成熟。
